# DAIC — технічні рішення PREP-01

Дата: 28.10.2026. Статус: рішення прийняті для першої локальної ітерації.

Вимоги: [MVP](daic_mvp.md). Порядок робіт: [підготовчий беклог](daic_preparation_backlog.md).

## Межі кроку

- **Джерело правди:** MVP визначає поведінку; цей документ визначає ідентичність і спосіб поставки. Під час роботи станом володіє головний процес Electron.
- **Backend-контракт:** головний процес керує вікном, треєм, одним екземпляром і позицією; renderer відображає персонажа. Зовнішній API не створюється. Детальний контракт належить PREP-04.
- **Done:** усі п’ять пунктів PREP-01 мають конкретні значення; вони звірені з MVP та вимогами пакування. Це завершення документального рішення, не перевірка працездатності застосунку.
- **Виключений обсяг:** код, генерація каркаса, встановлення пакетів, графіка, UI, збірка та запуск інсталятора.

Установлена програма працює локально без окремого HTTP-сервера. Службові файли Squirrel (`.nupkg`, `RELEASES`) є результатом maker; їх наявність не додає функцію автоматичного оновлення.

## 4. Каталог даних

- Постійний каталог налаштувань: `<appData>/DAIC`, де `appData` отримується через Electron `app.getPath('appData')`.
- На звичайній конфігурації Windows це `%APPDATA%\DAIC`. Не підставляти вручну `C:\Users\...`: профіль може мати інший шлях.
- Файл позиції: `settings.json` у `app.getPath('userData')`.
- Контракт майбутньої ініціалізації: до готовності застосунку й першого звернення до налаштувань встановити runtime-ім’я `DAIC`, забезпечити існування каталогу `<appData>/DAIC` і явно призначити його як `userData` через Electron API.
- Dev-запуск і встановлена версія в першій ітерації використовують однаковий каталог. Це дозволяє перевірити перенесення позиції між запусками; такі версії не тестувати одночасно. Перед тестами пошкодженого JSON робити резервну копію.
- Версія програми, поточна папка запуску й розташування exe не входять до шляху налаштувань.
- Формат JSON, перевірка координат, помилки доступу й відновлення описуються в PREP-04.

Звичайне оновлення збірки не повинно змінювати каталог. Поведінку даних після видалення програми перевірити на етапі приймання; автоматичне очищення даних у цьому кроці не планується.

## 5. Підписування та розповсюдження

Перший інсталятор призначений для локального ручного тестування й буде без цифрового підпису. Сертифікат, секрети підписування, автоматичні релізи, автозапуск і автооновлення в цій ітерації не додаються.

Перед зовнішнім поширенням окремо визначити видавця, ліцензію коду й ресурсів та потребу в підписуванні. Ці рішення не блокують локальну підготовку й не вважаються вже вирішеними. Фактичну реакцію Windows на інсталятор зафіксувати в прийманні.

## Перевірка PREP-01

- Платформа й архітектура відповідають наявному середовищу та Windows-обсягу MVP.
- Визначені обов’язкові для Squirrel метадані автора й опису; технічні імена без пробілів; App User Model ID узгоджений з іменами Squirrel та executable.
- Стабільний шлях налаштувань визначений незалежно від версії й папки встановлення.
- Пакування не додає зовнішнього API, автооновлення чи автопублікації.
- Відкритих питань, які блокують PREP-02, немає. Точні версії пакетів, ліцензія для поширення, графіка та фактична інсталяція мають власні наступні кроки.

Реальний користувацький сценарій поки не запускався: прикладного коду немає. Працездатність MVP не позначена як перевірена.

**Перезбірка:** не потрібна. **Перезапуск:** не потрібний. **Що перевірити зараз:** таблицю ідентичності й сталість шляху даних; при реалізації — записати позицію, завершити програму, встановити наступну збірку та перевірити відновлення позиції з того самого каталогу.
