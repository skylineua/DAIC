# DAIC — беклог підготовки до реалізації MVP

Дата: 28.10.2026. Основа: [план MVP](daic_mvp.md).

Поточний запит користувача перевів роботу до першого статичного етапу реалізації з ресурсами `source/`, без зміни графіки й без анімації. Актуальні межі — [опис етапу](daic_stage1_scope.md), фактичні результати й незавершене ручне приймання — [звіт](daic_stage1_verification.md). PREP-05/06 нижче збережені як вихідний план підготовки; фінальні ICO/інсталятор не оголошуються готовими. Webpack-специфікація PREP-03 замінена простішою збіркою tsc + Forge для цього етапу.

Це підготовчий беклог; виконані роботи позначаються окремо з посиланням на результат. Прикладний код, встановлення пакетів і генерація каркаса в межах підготовки цього документа не виконувались.

## 1. Рамки підготовки

- **Джерело правди:** вимоги — `Tasks/daic_mvp.md`; під час виконання застосунку — головний процес Electron; збережена позиція — локальний JSON у `app.getPath('userData')`.
- **Backend-контракт:** головний процес керує одним екземпляром, вікном, треєм і позицією. Renderer показує локальний PNG. Зовнішній HTTP API не потрібний. IPC додається лише за конкретної потреби, з вузьким типізованим контрактом.
- **Критерій done підготовки:** погоджені рішення, перевірене середовище, визначені пакети й правила вибору версій, готові ресурси та сценарії приймання. Підготовка не означає, що MVP працює.
- **Не робимо:** прикладний код, UI, встановлення залежностей, AI-інтеграції, автоматизацію релізів та функції за межами MVP.

Кожна задача нижче належить одному шару. Після підготовки реалізація йде окремо: головний процес → відображення → пакування й приймання.

## 3. Софт і залежності

### Обов’язковий софт

1. Windows для розробки й перевірки Windows-інсталятора.
2. Node.js 24 LTS і npm. Системний Node потрібен для інструментів розробки; Electron постачає власний runtime, а користувачеві встановленої програми Node окремо не потрібен.
3. Git і редактор коду — вже наявні.
4. Засіб перегляду PNG на світлому й темному тлі. Редактор із підтримкою alpha та експорту ICO потрібен лише якщо ресурси доведеться готувати локально; новий платний софт не є передумовою.

Docker, сервер, база даних, Python, Visual Studio Build Tools і Windows SDK не встановлювати наперед. Для обраного набору без власних native-модулів вони не є базовою вимогою. Якщо конкретний пакет потребуватиме додаткового інструмента, спочатку перевірити причину.

### Запропонований набір npm-пакетів

| Пакет / група | Призначення | Категорія |
| --- | --- | --- |
| `electron` | Runtime та API вікна, трея, моніторів і одного екземпляра | `devDependencies` |
| `typescript` | TypeScript і перевірка типів | `devDependencies` |
| `@types/node` | Типи для Node API головного процесу; підібрати до Node runtime обраного Electron | `devDependencies` |
| `@electron-forge/cli` | Локальні команди запуску, пакування, створення інсталятора | `devDependencies` |
| `@electron-forge/shared-types` | Типи конфігурації Forge | `devDependencies` |
| `@electron-forge/plugin-webpack` | Офіційний шлях збирання TypeScript через шаблон Forge | `devDependencies` |
| `webpack`, `webpack-cli`, `ts-loader` та loaders шаблону | Компіляція й обробка ресурсів; точний набір взяти з офіційного шаблону | `devDependencies` |
| `@electron-forge/maker-squirrel` | Windows-інсталятор `Setup.exe` | `devDependencies` |
| `electron-squirrel-startup` | Обробка службових запусків під час встановлення й видалення | `dependencies` |
| `@types/electron-squirrel-startup` | Типи, якщо обрана версія пакета не має власних | `devDependencies`, за потреби |

Базовий вибір — офіційний `webpack-typescript` шаблон Forge. Webpack тут є інструментом збірки, а не додатковим UI-фреймворком. Його dev server — частина локального циклу розробки; встановлена програма не повинна залежати від localhost або окремого сервера.

Vite поки не обираємо: офіційна документація Forge позначає підтримку як experimental. При створенні каркаса повторно перевірити цей статус; зміну рішення зафіксувати явно.

Точні версії Electron, Forge, TypeScript і Webpack не оголошуються сумісними до перевірки. Треба обрати стабільні релізи, перевірити `engines` і `peerDependencies`, узгодити версії пакетів Forge, зберегти `package-lock.json`. Не запускати генератор із плаваючим `latest` без фіксації фактично використаної версії.

Не потрібні: React, бібліотеки компонентів, Canvas/WebGL, Express, ORM, `electron-store`, `electron-updater`, бібліотека drag-and-drop. Для JSON достатньо `node:fs` і `node:path`; для перетягування спочатку розглянути штатну drag region Electron. Окремий preload не додавати, якщо renderer не потребує IPC.

## 5. Межа між підготовкою та кодом

До першого прикладного коду завершити PREP-01–04 і PREP-06. PREP-05 обов’язково завершити до фінальної реалізації відображення. Кожну задачу закривати за її результатом, а не через наявність цього списку.

Наступні кроки вже належать реалізації й виконуються окремо:

1. **Інструменти:** створити каркас, встановити погоджені пакети, зафіксувати lockfile, перевірити запуск шаблону, typecheck, package і make. Це перевірка інструментів, не приймання MVP.
2. **Головний процес:** один екземпляр, керування вікном, трей, позиція та fallback. Перевірити реальні сценарії цього шару з мінімальним технічним вмістом вікна.
3. **Відображення:** PNG, прозорість, розмір, перетягування, фокус і DPI.
4. **Поставка:** зібрати інсталятор і виконати повне ручне приймання встановленої версії.

Після кожного завершеного кроку записати: що зроблено; чи треба перезібрати; чи треба перезапустити; який сценарій перевірити й фактичний результат.
