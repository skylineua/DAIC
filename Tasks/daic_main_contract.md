# DAIC — контракт головного процесу PREP-04

Дата: 28.10.2026. Статус: контракт описано й звірено з вимогами; реалізація та runtime-перевірки ще не виконувались.

Це початковий контракт статичного етапу. Після його реалізації погоджено [доповнення моргання](daic_blink.md): вузький односторонній main→renderer сигнал видимості через preload. Нижче збережено первісний обсяг PREP-04; актуальні результати першого етапу — у [звіті](daic_stage1_verification.md).

Основа: [MVP](daic_mvp.md), [технічні рішення](daic_technical_decisions.md), [специфікація каркаса](daic_scaffold_spec.md).

## 1. Межі та джерело правди

- **Джерело правди під час роботи:** головний процес Electron. Поточні bounds беруться з BrowserWindow, видимість — через `isVisible()`. JSON є збереженим знімком позиції, не другим активним станом.
- **Backend-контракт:** main керує життєвим циклом, вікном, треєм і файлами налаштувань. Renderer показує локальний PNG та визначає штатну drag region. У MVP немає зовнішнього API, IPC чи preload.
- **Done цього кроку:** визначено власників логіки, дані, операції, переходи, fallback і сценарії перевірки. Документальний review не означає, що застосунок працює.
- **Виключений обсяг:** код, UI, стилі, генерація каркаса, встановлення пакетів, справжнє перетягування та приймання runtime.

## 2. Мінімальні модулі та залежності

Назви нижче — контракт майбутньої реалізації, файли в цьому кроці не створюються.

| Модуль | Відповідальність | Дозволені залежності |
| --- | --- | --- |
| `src/main/index.ts` | Ініціалізація, single-instance lock, Squirrel startup, обробники lifecycle; зв’язування сервісів | Electron app, сервіси, конфігурація |
| `SettingsService` | Читання/валідація JSON, запис знімка, локальна діагностика I/O | `node:fs`, `node:path`; переданий шлях файлу |
| `PositionService` | Початкова позиція, перевірка доступності, fallback за workArea | Передані прямокутники моніторів і розмір вікна; без renderer та файлової системи |
| `WindowService` | Єдине BrowserWindow, show/hide, bounds, debounce збереження, реакція на монітори | Electron BrowserWindow/screen/nativeImage, PositionService, SettingsService, конфігурація |
| `TrayService` | Іконка й побудова меню; делегування команд | Electron Tray/Menu, callbacks керування вікном і виходу |

Бізнес-правила позиції та налаштувань живуть у сервісах, не в entry point чи меню. DI-контейнер, event bus, універсальні repository-класи й базові service-класи не потрібні. TrayService не читає JSON, renderer не керує видимістю.

Основні операції сервісів:

| Власник | Операція | Результат / інваріант |
| --- | --- | --- |
| SettingsService | `load()` | Валідна позиція або `null`; очікувані помилки читання не виходять необробленими |
| SettingsService | `save(position)` | `saved` або `failed`; останній успішний запис не видаляється перед заміною |
| PositionService | `defaultPosition(primaryWorkArea, size)` | Нижній правий кут з відступом 24 DIP, наскільки дозволяє область |
| PositionService | `resolvePosition(candidate, workAreas, primary, size)` | Валідна доступна позиція або стандартна на основному моніторі |
| WindowService | `create()` | Один прихований екземпляр BrowserWindow; повторний виклик не створює другий |
| WindowService | `show()` / `hide()` | Ідемпотентна зміна видимості; show не викликає focus |
| WindowService | `returnToPrimary()` | Стандартна позиція на основному екрані, збереження, показ без focus |
| WindowService | `flushPosition()` | Скасувати debounce й синхронно спробувати зберегти актуальну позицію |
| TrayService | `refresh()` / `dispose()` | Меню відповідає фактичній видимості; іконка знищується лише під час завершення |

## 3. Єдина конфігурація персонажа

`src/shared/character-config.json` міститиме лише дані: `imagePath: assets/yi.png`, `height: 128`, `edgeMargin: 24`. Розмір і відступ — у DIP. Немає Node/Electron imports у shared-конфігурації.

Main знаходить PNG відносно кореня застосунку в dev або `process.resourcesPath` у packaged-режимі, читає розмір через nativeImage і обчислює ширину як `ceil(height × sourceWidth / sourceHeight)`. Нульовий/невалідний розмір — помилка ресурсу. Для прозорого вікна без рамки задається відповідний content size.

Renderer використовує ту саму висоту, пропорції PNG та розмір viewport; запас до цілого пікселя не повинен створювати scrollbar. Webpack alias `@daic-character` формується з `imagePath` цієї конфігурації; renderer імпортує alias як asset/resource. Це залишає один запис конкретного шляху PNG, зберігаючи bundling із PREP-03. Тип alias оголошується як рядковий URL.

Малі іконки трея й exe — окремі ресурси з уже визначених `assets/tray.ico` і `assets/app.ico`. Після заміни PNG перезбірка потрібна, зміна логіки не потрібна.

## 4. Налаштування та валідація

Файл: `<app.getPath('userData')>/settings.json`; стабільний userData: `<appData>/DAIC`, як у PREP-01.

```json
{
  "version": 1,
  "position": { "x": 1800, "y": 888 }
}
```

Правила читання:

1. Корінь — об’єкт, не `null` і не масив. `version` має дорівнювати числу `1`.
2. `position` — об’єкт; `x` і `y` — скінченні числа в допустимому діапазоні координат Electron (signed 32-bit). Рядки й перетворення типів не приймаються. Дробові координати округлюються до цілих DIP.
3. Від’ємні координати допустимі: монітор може бути ліворуч або вище основного. Додаткові поля ігноруються; під час запису формується лише визначена схема.
4. Відсутній файл, синтаксична помилка, невідома версія, неправильні типи або помилка читання → `null`, далі стандартна позиція. Міграції майбутніх схем у MVP немає.
5. Видимість, розмір вікна, ID монітора, тема, історія й дані renderer не зберігаються.

Некоректний файл не перезаписується лише через виклик `load()`. Після успішного розміщення вікна головний процес може зберегти вже перевірену поточну позицію за схемою v1. Це також може замінити файл невідомої версії; автоматичну сумісність із майбутніми версіями чи downgrade не обіцяємо. Перед ручними тестами робити backup.

## 5. Позиція та монітори

Усі обчислення використовують Electron DIP і `display.workArea`; фізичні пікселі та додаткове множення на `scaleFactor` не застосовуються. `screen` використовується після `app.whenReady()`.

Для workArea `(left, top, width, height)` і вікна `(W, H)` стандартна позиція:

- `x = max(left, left + width - W - 24)`;
- `y = max(top, top + height - H - 24)`.

Збережена позиція доступна, якщо весь прямокутник вікна вміщується в workArea хоча б одного поточного монітора. Перевіряються обидві осі й правий/нижній край; самого видимого кута недостатньо. Збережена позиція на межі двох моніторів нормалізується на основний екран під час наступного запуску або показу. Це просте правило MVP, без окремого алгоритму об’єднання областей.

Якщо позиція недоступна, використати стандартну на основному екрані. Не намагатися відновлювати ID від’єднаного монітора. Якщо робоча область менша за саме вікно, закріпити його на її початку; повне вміщення фізично неможливе й цей крайовий випадок фіксується як обмеження, а не спричиняє цикл переміщень.

При першому розміщенні, перед показом прихованого вікна та на `display-added`, `display-removed`, `display-metrics-changed` (bounds/workArea/scaleFactor/rotation) перевірити доступність позиції. Зміна моніторів не показує прихованого персонажа. Події моніторів об’єднати коротким debounce 250 ms, щоб не реагувати на кожен проміжний стан.

Під час drag не притискати вікно до меж. Після 250 ms без `move` прочитати актуальні bounds і зберегти координати без `setPosition`: пауза миші не доводить, що користувач відпустив кнопку. Доступність виправляється на запуску, перед показом або при зміні моніторів. Отже debounce не спричиняє стрибок посеред drag. Програмна зміна bounds теж приводить до збереження, але повторний запис незмінних координат пропускається. Не створювати рекурсивний цикл `move → setPosition → move`.

## 6. Запис та вихід

Для невеликого JSON обрано синхронний запис після debounce 250 ms. Це свідоме просте рішення: окрема async-черга, flush promises і бібліотека сховища не потрібні.

1. На `move` оновити таймер; не записувати JSON на кожен кадр.
2. При спрацюванні таймера прочитати актуальну позицію живого вікна, перевірити числовий формат і порівняти з останнім успішно збереженим значенням. Запис не рухає вікно; координати поза workArea перевіряються за правилами розміщення на наступному запуску/показі.
3. Записати повний JSON у `settings.json.tmp` в тому самому каталозі, потім замінити `settings.json` через rename. Не видаляти попередній settings-файл перед rename. Тільки власник single-instance lock виконує запис.
4. При помилці запису/заміни повернути `failed`, залишити актуальну позицію в пам’яті та попередній файл, наскільки це можливо. Невдале значення не вважати успішно збереженим; повторна спроба — наступна зміна, hide або quit, без нескінченних retries.
5. Тимчасовий файл не читати при наступному запуску. Його можна перезаписати наступною спробою; він не є джерелом правди. Rename зменшує ризик часткового JSON, але не гарантує збереження при збої живлення.
6. Перед hide, return-to-primary та штатним quit скасувати таймер і виконати `flushPosition()`; при quit — до знищення вікна. Якщо `save` знову не вдався, вихід усе одно завершується.

У `before-quit` встановлюється прапорець завершення; обробник close тоді не приховує вікно й не блокує вихід. Flush виконується один раз; dispose прибирає таймери та іконку. Примусове завершення процесу, вимкнення живлення й Windows logoff можуть не дати lifecycle-подій — це не гарантія останнього запису.

## 7. Життєвий цикл і стани

Стани описові: `starting`, `visible`, `hidden`, `quitting`. Окрема state-machine бібліотека не потрібна. Видимість не дублювати незалежним boolean, який може розійтися з BrowserWindow.

Порядок звичайного запуску:

1. Першими обробити Squirrel startup events: службовий запуск завершується без персонажа й трея.
2. Встановити стабільне ім’я `DAIC` і userData. Помилки доступу до settings переводять сховище в режим без збереження, якщо Electron може продовжити запуск; абсолютну працездатність Chromium з недоступним профілем не гарантуємо.
3. Отримати `requestSingleInstanceLock()`. Без lock — завершитися до створення вікна/трея й запису JSON. Обробник `second-instance` реєструється одразу після успішного lock.
4. Після ready отримати дисплеї, прочитати конфігурацію/ресурси й settings, визначити розмір/позицію, створити приховане вікно й трей. Тримати сильні посилання на них.
5. Завантажити renderer. Після готовності відображення показати через `showInactive()`, оновити меню. Не викликати `focus()`/`app.focus()`.
6. Якщо `second-instance` надійшов під час starting, запам’ятати запит показу й виконати після готовності. Нове вікно не створювати.

| Подія / команда | Початковий стан | Результат |
| --- | --- | --- |
| Успішний запуск | starting | visible, один персонаж і один трей |
| «Приховати Ї» | visible | flush, hidden, процес і трей залишаються |
| «Показати Ї» | hidden | перевірка позиції, showInactive, visible |
| Повторні show/hide | відповідний стан | без дублювання вікна чи side effects |
| «Повернути на основний екран» | visible або hidden | стандартна позиція, flush, showInactive, visible |
| Повторний звичайний запуск | visible або hidden | другий процес завершується; перший перевіряє позицію й показується без focus |
| Зміна моніторів | visible або hidden | доступна позиція; попередня видимість збережена |
| Системний close вікна | visible | перехопити й виконати hide, якщо це не quit |
| «Вийти» | visible або hidden | quitting → flush → закриття/знищення → процес і трей завершено |

Перший запуск після звичайного виходу завжди показує персонажа: hidden не записується на диск. Single-instance означає один головний екземпляр застосунку, а не один OS-процес: Electron має допоміжні процеси.

## 8. Вікно, drag і фокус

Базові параметри: `frame: false`, `transparent: true`, `show: false`, `alwaysOnTop: true`, `skipTaskbar: true`, `resizable: false`, `maximizable: false`, `minimizable: false`, `fullscreenable: false`, `focusable: false`, без меню та стандартних декорацій. Розмір близький до PNG, не повноекранний overlay.

Renderer задає прямокутну штатну drag region на персонажі, вимикає виділення тексту та HTML image-drag. Main отримує рух із подій вікна, не з IPC миші. Не застосовувати `setIgnoreMouseEvents(true)`: це відключило б і перетягування. Точного click-through за alpha немає.

Одиночний/подвійний клік і наведення не запускають дій; maximize вимкнений. Меню керування є в треї. Поведінку системного контекстного меню на drag region перевірити на Windows; не додавати власне меню поверх персонажа.

**Обов’язкова перевірка перед завершенням шару відображення:** `focusable: false` + native drag повинні разом дозволяти рух без стрибків і не забирати введення з редактора. Документація не доводить цей комбінований сценарій на нашій машині. Якщо він не проходить, зупинитися, записати фактичний результат і явно переглянути контракт; не вводити мовчки focus, custom drag/IPC або native-залежності.

## 9. Трей, безпека та помилки

Трей має три дії: «Приховати Ї»/«Показати Ї» залежно від `isVisible()`, «Повернути на основний екран», «Вийти». Після кожної зміни видимості оновлюється меню. Лівому кліку/подвійному кліку по іконці не призначати додаткових команд.

WebPreferences: `nodeIntegration: false`, `contextIsolation: true`, `sandbox: true`, `webSecurity: true`. Не надавати renderer filesystem/shell API, дозволи пристроїв чи нові вікна. Заборонити довільну навігацію та `window.open`; не відкривати зовнішні URL. Завантажується лише entry Forge: у dev дозволені потрібні локальні з’єднання dev server/HMR, у packaged — локальні файли.

CSP: scripts/resources — власні; `object-src 'none'`, `base-uri 'none'`; мережевий `connect-src` в packaged — `'none'`. Поточний style-loader вставляє style tags, тому для стилів потрібен сумісний `style-src` (у першому каркасі допускається `'unsafe-inline'` тільки для styles). Не поширювати цей дозвіл на scripts; dev-HMR CSP налаштовувати окремо від packaged і перевіряти після make.

| Помилка | Поведінка |
| --- | --- |
| Немає/пошкоджений settings, недоступний монітор | Стандартна позиція, запуск продовжується |
| Немає прав запису settings | Сеанс працює з позицією в пам’яті; локальна діагностика; quit не блокується |
| PNG не знайдений/пошкоджений, іконка трея непридатна | Показати коротке native-повідомлення про помилку ресурсу й завершити процес; не лишати недоступний процес без керування |
| Renderer не завантажився або аварійно завершився | Коротке native-повідомлення й штатне завершення; автоматичний restart/reload у MVP не додається |
| Неочікувано знищене вікно | Прибрати трей і завершитися; не створювати приховано новий персонаж |

Діагностика — невеликий текстовий `daic.log` у userData: остання помилка settings/ресурсів, код I/O, час; максимальний розмір 64 KiB, при перевищенні почати файл заново. Без даних інших програм і телеметрії. Якщо запис діагностики неможливий — console warning без рекурсивного логування; додаткова logging-бібліотека не потрібна. Звичайні fallback налаштувань не відкривають діалоги. Native-повідомлення про фатальну помилку — винятковий шлях, не екран налаштувань.

## 10. Перевірка контракту на сценаріях

Це очікувані результати документального розбору; статус усіх runtime-сценаріїв — **not tested**. У прикладах розмір вікна умовний `96 × 128` DIP, а не вимога до пропорцій фінального PNG.

| Вхід / дія | Очікуваний результат |
| --- | --- |
| Немає JSON; workArea `(0,0,1920,1040)` | `(1800,888)`, visible |
| JSON v1, позиція `(200,300)` у тій самій області | Відновити `(200,300)` |
| `x: "200"`, `version: 2`, масив або зламаний JSON | Відкинути, стандартна позиція |
| Другий монітор workArea `(-1280,0,1280,984)`, позиція `(-500,200)` | Залишити: від’ємний x валідний |
| Та сама позиція після від’єднання другого монітора | Повернути на основний `(1800,888)` |
| Позиція `(1900,900)`, primary як вище | Прямокутник виходить праворуч — fallback |
| Рух в інше місце → «Вийти» раніше 250 ms | Flush актуальної позиції до знищення вікна |
| Помилка запису → hide → show → quit | Сеанс продовжується, старий JSON збережений, вихід не зависає |
| Hide → повторний запуск | Один персонаж стає visible, другий main завершується |
| Hide → від’єднання монітора | Позиція виправлена, персонаж лишається hidden |
| Hide → «Повернути на основний екран» | Стандартна позиція, персонаж visible |
| Повторний запуск до ready | Запит показу відкладено до готовності, другого вікна немає |
| Перехід між 100/125/150% DPI | Позиція перевірена у DIP, фізичний scaleFactor вдруге не застосований |
| Службовий запуск Squirrel | Без персонажа/трея та звичайного запису settings |
| Немає придатної іконки трея | Помилка ресурсу, повне завершення замість некерованого процесу |

Звірено покриття пунктів PREP-04 та відсутність зовнішнього API/нових залежностей. Реальні перевірки backend і drag/focus виконуються лише після створення відповідного шару. Повний протокол приймання — PREP-06.

**Перезбірка зараз:** не потрібна. **Перезапуск зараз:** не потрібний. **Що перевірити зараз:** таблиці переходів і очікуваних результатів. **Що перевірити при реалізації:** один екземпляр, hide/show/quit, запис/відновлення/fallback, потім native drag без втрати фокуса, DPI та встановлена версія.
